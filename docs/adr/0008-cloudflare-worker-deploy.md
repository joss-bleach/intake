# Production deploy: single Cloudflare Worker, Alchemy-provisioned

**Status:** accepted

**Context:** Issue #97 asked for a production deploy: the `node:http` server ported to a Cloudflare Worker, static assets served from the same Worker, Postgres reached via a Hyperdrive binding, infra provisioned through Alchemy, and both deferred cron TODOs (#49 tripwire, #44 OFF delta-refresh) resolved.

**Decision:**

- **Worker, not two services.** One Worker `fetch` handler (`src/server/worker.ts`) serves the built SPA (via a Workers `Assets` binding, `run_worker_first` scoped to `/api/*` and `/trpc/*`) and the API (tRPC's `fetch` adapter, betterauth's Web-standard `auth.handler`). Same origin in production, so CORS is dead weight there — it's kept only in `src/server/dev-server.ts`, the Node `http` bridge used for local dev (Vite on :5173 against the server on :3001), and never ships to the Worker.
- **`pg` + Hyperdrive, not `@neondatabase/serverless`.** The ticket's wording suggested Neon's serverless driver. That driver's own docs recommend Hyperdrive+`pg` instead specifically for Workers, and its WebSocket-based `Pool`/`Client` must be opened and closed within a single request — incompatible with this codebase's module-level singleton `db`/`pool` (used across every router and ~17 test files). Hyperdrive's supported pattern is the standard `pg` driver over `cloudflare:sockets` (enabled by the `nodejs_compat` flag), so the same `pg` driver works everywhere; only the connection string's source differs — in production `worker.ts` reads Hyperdrive's `connectionString` inside each handler (never at module scope — Cloudflare's upload validation rejects it as error 10021, see issue #107) and scopes a per-request pool via `createDb`/`withDb` in `db.ts`; everywhere else the module-level singleton connects with plain `DATABASE_URL`.
- **`CloudflareStateStore`, not D1/R2.** The ticket said "D1 or R2" for remote Alchemy state; both are deprecated as state-store backends in Alchemy 0.94.0 in favour of `CloudflareStateStore`.
- **No separate `DnsRecords` resource.** `Worker.domains` already provisions and manages the custom domain's DNS via Alchemy's `CustomDomain` resource. A second, empty `DnsRecords` call would be pure ceremony.
- **OFF ingest (#44) stays a scheduled GitHub Actions job**, not a Worker cron. It streams a multi-GB dump from local disk (`createReadStream`) — a Worker has no filesystem and no room to buffer a download that size. The tripwire (#49) is a genuine Worker cron (`scheduled` export, daily). `.github/workflows/off-ingest.yml` downloads the OFF dump and runs `pnpm food:ingest-off` against Neon directly, bypassing Hyperdrive (Hyperdrive only exists as a Worker binding). Upserts on `(provenance, external_id)`, so re-running is safe.
- **Migrations run inside `alchemy.run.ts`**, right after `NeonProject` is created, against a throwaway `pg`/`drizzle` instance pointed straight at Neon's connection string. It calls drizzle's migrator directly, not `src/server/db/migrate.ts`: the alchemy CLI loads `alchemy.run.ts` with plain Node, which cannot resolve the app's extensionless imports. Running it here — rather than as a separate CI step — sidesteps a chicken-and-egg problem: Neon's connection string doesn't exist as a static secret until `NeonProject` provisions it, and it's idempotent, so every deploy is safe to re-run.
- **Deploy runs after CI, on `main` only.** `.github/workflows/ci.yml` gained a `deploy` job (`needs: ci`, `if: refs/heads/main` push) that builds the SPA and runs `pnpm infra:deploy`.

**Consequences:** Local dev (`pnpm dev`) is unaffected — `dev-server.ts` still wraps `node:http` and talks to the docker-compose Postgres directly. The OFF-ingest workflow needs its own direct-to-Neon `DATABASE_URL` secret (`OFF_INGEST_DATABASE_URL`), separate from the Worker's Hyperdrive-mediated one — this isn't part of `scripts/production-setup.sh` and needs adding by hand. If a future need for edge-native Postgres access (outside Hyperdrive's pooling) arises, revisit the serverless-driver decision above; today's architecture doesn't need it.
