# Model selection methodology

**Status:** accepted

**Context:** Three model roles need picking — vision primary (label-photo OCR, cheap/fast tier), vision fallback (the ADR 0001 retry-on-`ParseFailure` model, cost-agnostic), and text/description parsing (single model, no fallback tier — its own retry re-tries itself). Full rubric discussion: [Model selection methodology](https://github.com/joss-bleach/intake/issues/7). Candidate research: [vision-model-candidates](https://github.com/joss-bleach/intake/tree/research/vision-model-candidates/docs/research/vision-model-candidates.md) (issue #23), [text-model-candidates](https://github.com/joss-bleach/intake/tree/research/text-model-candidates/docs/research/text-model-candidates.md) (issue #24). Scoring itself needs the eval harness ([Eval harness + dataset design](https://github.com/joss-bleach/intake/issues/6)) to exist and a provisioned `OPENROUTER_API_KEY`, neither of which exist yet — [Run model-selection bake-off](https://github.com/joss-bleach/intake/issues/25) confirmed this is real build-phase work, not a cheap task, and was closed out of scope for the architecture-spec map. This ADR records the decided *methodology* — rubric, candidate shortlists, process — below, and the actual picks from the real run (issue #54) further down.

**Decision:**

**Scoring rubric.** Gate on the brief's accuracy floor first — label reads ≥95/100, description parses ≥85/100 — scored by the same eval harness from #6, reused unmodified against each candidate model. Among candidates clearing the floor:

- **Vision primary** and **text parsing**: pick cheapest, latency as tiebreaker.
- **Vision fallback**: pick highest accuracy alone, cost and latency ignored — it's the rarely-used retry path, so clearing the failures the primary couldn't matters more than its price.

**Candidate pool.** Not hand-curated — sourced via two dedicated research tickets, one per model type, each pulling current vision-capable / text-capable OpenRouter models with pricing and any available benchmark signal.

**Vision candidates ([#23](https://github.com/joss-bleach/intake/issues/23)):**

*Primary tier (cheap-fast):* `google/gemini-2.5-flash-lite`, `qwen/qwen3-vl-30b-a3b-instruct` (or `qwen3-vl-8b-instruct`), `openai/gpt-4o-mini`, `mistralai/mistral-small-3.2-24b-instruct`.

*Fallback tier (cost-agnostic):* `google/gemini-2.5-pro`, `openai/gpt-5`, `anthropic/claude-opus-5` / `anthropic/claude-sonnet-5`, `qwen/qwen3-vl-235b-a22b-instruct`.

**Text candidates ([#24](https://github.com/joss-bleach/intake/issues/24)):** `qwen/qwen3-30b-a3b-instruct-2507`, `openai/gpt-4.1-nano`, `google/gemini-2.5-flash-lite`, `openai/gpt-4o-mini`, `deepseek/deepseek-chat-v3.1`, `anthropic/claude-haiku-4.5` — spanning roughly a 100x price range.

Both research tickets flag some cited benchmark numbers as sourced from secondary coverage or not independently re-extracted this session ("re-pull before load-bearing") — the bake-off run should re-verify anything load-bearing rather than trust the citation as-is.

**Cadence.** One-time bake-off at MVP launch; re-run only on a trigger (a candidate model is deprecated, its pricing shifts, or a notable new entrant appears) — no fixed re-run schedule.

**Actual picks (bake-off run 2026-08-13, issue #54):**

| Role | Model | Notes |
|---|---|---|
| Vision primary | **`google/gemini-2.5-flash-lite`** | Cheapest working candidate by a wide margin; transcribed a real UK label correctly in the live spot-check below. |
| Vision fallback | **`qwen/qwen3-vl-235b-a22b-instruct`** | Tied on accuracy with every other working candidate in the spot-check; the one candidate whose *own* dedicated OCR-benchmark table (CC-OCR/OmniDocBench/OCRBench/OCRBench_v2) was run on this exact checkpoint, not inherited from a larger/smaller sibling; also far cheaper than the alternatives despite cost being deprioritized for this tier. |
| Text/description parsing | **`deepseek/deepseek-chat-v3.1`** | Best real accuracy among candidates that actually worked against our schema; the only candidate to get a gram-quantity item fully right under the harness's prompt. |

**How the run actually went (deviations from the methodology above, and why):**

- **The eval harness's committed fixtures couldn't gate this run as designed.** The one label fixture (`weetabix-original.png`) is a synthetic placeholder image, not a real label — every vision candidate reads it as confident garbage, so the ≥95% floor can't be honestly cleared by anyone against it. The two description fixtures use the harness's own deliberately plain, non-production prompt (`src/eval/prompts.ts` — explicitly *not* issue #46/#47's real prompt), which also kept every text candidate under the ≥85% floor. In both cases the harness's job — reused unmodified, per this ADR's original decision — was to gate on floor-clearing; instead, for this seed dataset, it produced a "nobody clears the floor" result that reflects the seed data/prompt weakness rather than genuine model incapability. The `pnpm eval` CI gate itself is unaffected — its committed cache is hand-authored seed data, deliberately untouched by this bake-off (see below).
- **Vision picks are therefore based on a live spot-check against a real UK nutrition-label photo** (a nutrition panel with no product name/brand visible), run ad hoc against every candidate and not committed to the repo — the source photo was a watermarked stock image, unsuitable to redistribute as a fixture. Every candidate that could execute at all read every printed nutrient value correctly (energy, protein, carbohydrate, sugars, fat, saturates, fibre; "trace" salt handled sensibly). That flattened the primary tier to a pure cost decision and left the fallback tier decided on secondary signal (re-verified benchmark ownership) rather than a harness accuracy gap, since there wasn't one to measure. **Fast-follow:** replace the synthetic label fixture with a real, appropriately-licensed photo (already tracked in `src/eval/README.md`) and re-run once it lands.
- **Text picks are based on a real harness run against the committed description fixtures**, so this part is a genuine (if floor-missing) result: `deepseek/deepseek-chat-v3.1` scored 1/2 (the only candidate to convert "a medium banana" to grams correctly); every other working candidate scored 0/2, mostly by defaulting to `quantity: 1` in whatever unit the prompt didn't rule out. This is a real quality signal, not just a price ranking — DeepSeek is not the cheapest candidate (`qwen/qwen3-30b-a3b-instruct-2507` is, and scored 0/2, dropping a whole ingredient), but it's the only one demonstrating real unit-conversion reasoning under the harness's intentionally thin prompt, at a still-modest price. **Fast-follow:** re-run against issue #46's real production prompt once description-path prompt tuning stabilizes — the ranking may change under a prompt that actually specifies units.
- **Two OpenAI-family candidates were disqualified by a real schema-compatibility failure, not an accuracy result**, discovered while running this bake-off: `openai/gpt-4o-mini` and `openai/gpt-5` both hard-errored on the label schema ("`required` is required to... include every key in properties, missing 'brand'" — OpenAI's strict structured-output mode rejects Effect's JSON-Schema-optional encoding of `brand`/`servingSize`), and `openai/gpt-4.1-nano` hard-errored on the description schema ("`$ref` cannot have keywords {'additionalProperties'}" — a conflict between Effect's `$defs`/`$ref` schema shape and OpenAI's strict-mode validator). `openai/gpt-4o-mini` happened to work for the *description* schema (no optional fields there) despite failing for the *label* schema — the failure is schema-shape-dependent, not a blanket "OpenAI doesn't work." No fix was attempted (would mean generically reshaping every schema's optional-field/`$ref` encoding for one vendor family) since neither disqualified candidate was on track to win its tier on price or accuracy anyway. Left as a known gap if an OpenAI-family model is ever reconsidered.
- **Fixing this bake-off required a real bug fix first.** Running any live call at all surfaced that this ADR's own assumption in ADR 0004 — "an Effect Schema converts to a Standard Schema via `Schema.standardSchemaV1`, which `generateObject`'s `schema` option accepts directly" — was untested and wrong: Effect's Standard Schema output has no `~standard.jsonSchema` converter, so every real `generateObject` call failed before reaching the network, regardless of model. Fixed in `src/ai/effect-ai-sdk.ts` (`toGenerateObjectSchema`, built from `JSONSchema.make` + `Schema.decodeUnknownEither` instead) — this is what made *any* part of this bake-off possible, and is now the mechanism every live call in the app goes through, verified by a real round-trip in `test/integration/ai-sdk.test.ts`.
- **Citations re-verified per this ADR's "re-pull before load-bearing" flag**, to the extent tooling allowed: the Qwen3-VL technical report's own text (fetched directly, not via secondary summary) confirms in its own words that "the Qwen3-VL-235B-A22B-Instruct model establishes a new state of the art" on CC-OCR/OmniDocBench/OCRBench/OCRBench_v2 — a stronger re-confirmation than the original research's "benchmark axis exists" framing, though the exact numeric table (referenced as being in the paper's Section 5.4) still isn't extractable through available fetch tooling, same limitation the original research hit. OpenAI's GPT-4.1 announcement page still 403s to a direct fetch, so its IFEval citation remains unverified at primary source, unchanged from the original research (not load-bearing for the final picks above, since text/vision decisions rested on the live bake-off, not this citation).

## Considered options

- **Hand-curate the candidate shortlists** — rejected: risks missing cheaper or better-benchmarked entrants on a fast-moving model marketplace; dedicated research tickets keep sourcing current and repeatable for the eventual re-run.
- **Uniform cheapest-wins rule across all three roles** — rejected for the fallback tier: a cost-agnostic, highest-accuracy pick is the point of having a fallback tier at all — a fallback picked on price would just be a second primary.
- **Run the bake-off now, inside this map** — rejected: it needs an eval-harness implementation and a provisioned OpenRouter key, neither of which exist in this spec-only repo; ruled out of scope by [#25](https://github.com/joss-bleach/intake/issues/25) rather than stretched into a "cheap task ticket."
- **Fixed re-run schedule (e.g. quarterly)** — rejected: model pricing and capability shift on vendor timelines, not calendar ones; trigger-based re-runs (deprecation, price change, notable new entrant) avoid both stale picks and needless re-runs.

## Consequences

- The bake-off ran (issue #54, 2026-08-13) and the three picks above are wired into the real pipelines (`env.ts`'s `LABEL_VISION_MODEL`/`LABEL_VISION_FALLBACK_MODEL`/`DESCRIPTION_PARSE_MODEL` defaults) — this ADR is now actionable.
- Because scoring reuses #6's harness unmodified, the harness's tolerances (±2% label reads, ±15% description parses) and fixture set are load-bearing for this decision too — and, as it turned out, the *seed* fixture set (one synthetic label photo, a placeholder prompt for description) wasn't strong enough to gate on floor-clearing for real; see "How the run actually went" above for what filled that gap this time, and the fast-follows for closing it properly.
- The vision-fallback pick is deliberately not the vision-primary pick's cheaper sibling — it's optimized for a different objective (accuracy, not cost) from the same run, so the two picks may come from different model families entirely. In this run they did (Google primary, Qwen fallback).
- Re-verifying the "re-pull before load-bearing" benchmark citations from #23/#24 was done to the extent available tooling allowed (see above) — exact numeric tables for Qwen3-VL's OCR benchmarks and OpenAI's GPT-4.1 IFEval score remain unextracted, same gap the original research flagged.
- Running this bake-off surfaced and fixed a real, previously-untested bug in ADR 0004's vendor wrapper (Effect Schema → AI SDK schema conversion never actually worked against a live model) — every real `generateObject` call in the app was broken until this ADR's own bake-off exercised one for the first time. See `src/ai/effect-ai-sdk.ts`.
- Two OpenAI-family candidates (`openai/gpt-4o-mini` as a vision candidate, `openai/gpt-4.1-nano`) are known-broken against our current schema shapes (strict structured-output mode rejects Effect's optional-field and `$defs`/`$ref` encodings) — not fixed, since neither was on track to win; worth revisiting before ever picking an OpenAI-family model for either tier.
